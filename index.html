Abstract. Frame allocation has two layers. A quota policy (Equal or Proportional) decides how many frames each process may hold. A physical allocator decides which frames it gets and how fast. On a multi-core cloud database server the second layer becomes the bottleneck: the buddy allocator slows from 13 ns to 2.5 µs per allocation as cores are added, and it scatters concurrent processes across memory, which destroys the 2 MiB regions that huge pages need. We implement LLFree-lite, a simplified version of the lock-free LLFree allocator (USENIX ATC '23), and compare it with a textbook buddy allocator and a buddy allocator with Linux-style per-CPU lists on a 6-core / 12-thread AMD Ryzen 5 5600H.

Paper §4.1 · The lock is the bottleneck

Race the allocators

Each dot is a CPU core asking for a frame. Add cores and watch what happens at the lock. The paper measured the global-lock buddy allocator going from 12.8 ns to 2,481 ns per allocation, a 194× slowdown, with 41% of lock acquisitions finding the lock already taken.

workingwaiting for the lockholding the lock / finishing an allocation

How the model works. Time advances in steps. A core needs one step of work per allocation. Buddy takes the lock for every allocation (hold: 1 step). Per-CPU lists take it for every 32nd allocation to refill a batch (hold: 3 steps). LLFree-lite never takes a lock because each core has a private reserved tree. The model shows the mechanism. Magnitudes differ from the hardware measurements, where cache-line bouncing makes the lock far more expensive than a single step.

Paper §4.2 and Figure 2 · Interleaving destroys huge pages

Fill memory, then let queries exit

Twelve processes run on twelve CPUs and each faults in one frame per tick until it reaches its quota. The model has 64 regions of 64 frames. A region that is completely free could hold a huge page. Press Terminate finished processes to release the six that exit.

Buddy (global lock)

LLFree-lite

Simplified model. Buddy gives each request the lowest free frame. LLFree-lite gives each CPU its own 128-frame tree, prefers partly used trees when it needs a new one, and falls back to taking any free frame if memory runs out. The paper's Figure 2 reports 17 free regions for buddy and 38 for LLFree-lite with the same quotas. This simulation counts its own run, so the exact numbers can differ.

Paper §5 · Design of LLFree-lite

Step inside the allocator

One CPU owns a reserved tree of four 2 MiB regions. Allocate and free frames and watch which counters move. The pseudocode lines that ran are highlighted. Count how few of the operations are shared atomics, and how none of them is a lock.

1 row = one u64 word · 8 words = 64 bytes = one cache line

        

      

    

    
Why it scales. A CPU reserves a tree by swapping the shared tree counter for RESERVED and keeping the free count in a private variable. Allocations then decrement that private integer instead of a shared one. A frame freed by another CPU goes back through an atomic increment of the shared tree counter, and the owner collects those later with one atomic exchange. Counters are decremented before bits are set and bits are cleared before counters are incremented, so a successful decrement guarantees the bit search will succeed.

Paper §6.6 · Memory overhead
How much metadata does the allocator need?

  
LLFree-lite keeps one bit per frame, a 4-byte counter per 2 MiB region and a 4-byte counter per 32-region tree. Our buddy implementation keeps two 32-bit list links and an order byte per frame. A real kernel hides those links inside its existing per-frame descriptor, so the exact factor is specific to our buddy code.

  

    
    

    

  







  
Paper §6.8, §7 and §8
What to take away

  

    
Allocation is its own layer
Proportional allocation divides memory better than Equal allocation. On a multi-core host the allocator underneath the quota decides whether that memory arrives quickly and in huge-page-sized pieces.

    
Where buddy still wins
When a core frees a frame and immediately allocates again, per-CPU lists hit a private cache and never touch the lock. They need 14.1 ns per pair against 18.9 ns. LLFree-lite still does real atomic updates on every operation.

    
Next step
A small per-CPU cache in front of LLFree should keep the same-core fast path and the lock-free scalability. That combined design is the authors' proposed follow-up.

  

  

    
Threats to validity

    
The experiments run in user space on Windows 11, not inside a kernel. Thread pinning uses SetThreadAffinityMask, and the scheduler and SMT siblings add noise, reduced by taking the median of five runs. The buddy baselines follow the textbook and per-CPU designs. They are not the full Linux implementation, which also has migrate types, watermarks and compaction. The results are an algorithmic comparison, not a claim about a particular Linux version. A 6-core machine limits how far scaling can be observed, and LLFree's original evaluation goes to far higher core counts. LLFree-lite omits persistence, supports only orders 0 and 9, and leaves out the "steal" path used when memory is nearly exhausted.
